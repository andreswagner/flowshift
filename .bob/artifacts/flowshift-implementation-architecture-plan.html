FlowShift — Implementation Architecture Plan

Pentaho → IBM DataStage migration framework · AI-powered, open-source, GitHub-driven

1. What already exists and what it tells us

The repository already contains all three layers in working, well-factored form:

  • migration-app/ — plain ES-module UI, no build step, IBM Carbon CSS, delegated event model, full mock in-browser for offline dev.
  • server/app.py — Flask gateway with configurable upstream mapping, mock mode, admin-guarded settings routes, secret masking, deep-merge config. The gateway shields the browser from every upstream detail.
  • server/openapi.yaml — clean OpenAPI 3.1 contract defining the migration lifecycle and all response shapes, ready for a real backend team to implement.

What is not yet present: tests, CI, the actual AI translation engine, and the GitHub workflow infrastructure needed to evolve the project safely. This plan covers all of that.

2. Runtime architecture

Browser — migration-app/
Plain JS modules + IBM Carbon CSS. No framework, no build step. Calls only /api/… and /admin/… on the same origin.
▼
Flask Gateway — server/app.py
Stable route contract for the UI. Holds secrets. Forwards calls to the upstream API using configurable paths, method, auth and response-field mapping stored in config.json. Also serves the static UI from migration-app/.
▼
Migration API — server/openapi.yaml (backend team implements)
Async translation engine: parses .ktr / .kjb XML, reads the functional document via an LLM, maps Pentaho steps to DataStage stages, and emits a .dsx export. Lifecycle: draft → queued → running → succeeded | failed | cancelled.

Key invariant: migration-app/api.js and server/app.py are the only two files with seams to the outside world. Every new platform adapter, new auth scheme, or new response shape should be expressible through config and a mapping change in those two files, not a new dependency.

4. UI component model

The UI deliberately uses no framework. The existing pattern — a single state object, a render() function that rewrites DOM sections, and a single delegated event listener — is the right model. Keep it.

Module / functionResponsibilityExtension points
app.js · render()Full re-render from state. Calls view*() helpers.Add a new phase by adding a view*() function and a branch in render().
app.js · stateSingle source of truth: phase, files, migrationId, result, settings, flags.Add new top-level keys; never mutate nested objects — always replace them.
api.js · realAll HTTP calls. Maps to the gateway's stable /api/* contract.To add an endpoint, add a method here and a corresponding route in app.py.
mock-api.jsIn-browser simulation, same function signatures as api.js.Mirror every new api.js method here so offline development stays complete.
settings.jsAdmin dialog for gateway config. Reads/writes /admin/config.Add a new config section by adding a <fieldset> to form() and a matching field in collect().
config.jsGateway URL, poll interval, auth header hook.Swap getAuthHeaders to inject a per-request token (e.g. from sessionStorage).

Phase state machine

upload  ──[start]──►  translating  ──[complete]──►  complete
  ▲                        │
  └──[cancel / failed]────┘        reset ──► upload (new migrationId)

Only three UI phases; each maps to exactly one view*() function. The phase key in state drives the entire render — no conditional CSS classes scattered across the DOM.

5. Data service abstraction

Browser side (api.js)

  • One http(path, opts) helper — throws a typed error with status and code.
  • Seven named functions: createMigration, uploadFile, removeFile, start, cancel, getStatus, download.
  • Exports either real or mock depending on config.USE_MOCK.
  • No global state, no caching — callers own retry / backoff logic.

Gateway side (app.py)

  • upstream(method, path, …) — single function that builds auth headers, makes the request, handles TLS.
  • dig(obj, path) — dotted-path reader for response mapping.
  • normalize_status(body, rm) — maps any upstream shape to the UI's MigrationStatus.
  • fail_from(r, cfg) — turns upstream errors into {code, message} the UI understands.

When connecting a new upstream API, only config.json needs to change — not code. The responseMap section handles field renaming; the statusValues map handles status-word differences; stepIsPercent handles progress-unit differences.

6. State management strategy

The existing approach is correct and should not be replaced with a framework. The rules to enforce:

  1. One state object, never duplicated into DOM attributes or module-level variables.
  2. State transitions are synchronous — async operations update state after await, then call render().
  3. No intermediate renders during an async sequence — set all state changes, then call render() once.
  4. Guards prevent double-submission: state.starting and state.downloading flags disable buttons during in-flight calls. Mirror this pattern for every new async action.
  5. Polling is owned by the state machine: poll() starts, stopPoll() stops. Never start a second poll without stopping the first.
  6. Server-side config is not in client state: gateway settings live in server/config.json and are loaded on demand by settings.js via /admin/config.

7. Error handling

LayerError typeHandling
Browser — file validation Wrong extension, empty file Synchronous, before upload. Sets item.state = 'bad', shows inline error under the file row. No toast — the error stays visible.
Browser — upload rejection 4xx from gateway (invalid file type, file too large) Sets item.state = 'bad' with the detail text from the upstream problem response. The user can fix and re-upload without losing other files.
Browser — transient network fetch throws, or 5xx from gateway Toast notification, 6 s auto-dismiss. Polling errors are swallowed silently to avoid spamming the user during brief outages.
Browser — translation failure status === 'failed' from status poll Returns phase to upload. Shows the error.detail text in a toast (the OpenAPI contract guarantees this is safe to show verbatim to users).
Gateway — upstream unreachable requests.RequestException Returns {code: "UPSTREAM_UNREACHABLE", message: "Could not reach…"} as HTTP 502.
Gateway — upstream error 4xx/5xx from upstream fail_from() extracts the problem detail using the responseMap.errorMessage path, passes status through for 4xx, returns 502 for 5xx.
Gateway — config invalid Bad base URL, unknown auth type, etc. validate(cfg) returns a list of errors before saving. Settings dialog shows them inline.
Gateway — admin unauthorized Missing or wrong X-Admin-Token Returns 401. UI prompts for the token (stored in sessionStorage, not localStorage) and retries automatically.
Never expose stack traces or internal paths to the browser. The gateway's error helpers already follow this rule — keep it. Log verbosely server-side; send only message and code client-side.

8. Test strategy

Gateway unit tests — tests/gateway/ (pytest)

  • test_config.py: deep_merge, validate, masked, save/load round-trip. No network.
  • test_normalize_status.py: All combinations of upstream shapes against normalize_status() — this is the highest-risk function and deserves the most cases.
  • test_mock.py: Full happy path through mock mode using Flask's test client. No requests or real HTTP involved.
# example — normalize_status round-trip
def test_succeeded_maps_output():
    rm = json.loads(DEFAULT_PATH.read_text())["responseMap"]
    body = {"status": "succeeded", "progress": {"percent": 100},
            "result": {"artifact": {"fileName": "x.dsx"}, "summary": {...}, "items": [...]}}
    out = normalize_status(body, rm)
    assert out["status"] == "complete"
    assert out["output"]["fileName"] == "x.dsx"

Gateway integration test — tests/gateway/test_proxy.py (pytest + responses)

Use the responses library to intercept requests calls. Test that auth headers, path templates, and config-driven field extraction work end-to-end without real network.

Contract fuzz — tests/contract/test_openapi.py (Schemathesis)

import schemathesis
schema = schemathesis.from_path("server/openapi.yaml", base_url="http://127.0.0.1:5000/api")
@schema.parametrize()
def test_api(case): case.call_and_validate()

Runs against the gateway in mock mode. Catches shape regressions between openapi.yaml and normalize_status() automatically.

E2E browser tests — tests/ui/ (Playwright)

SpecWhat it covers

9. Local validation steps

  1. Start the gateway in mock mode
    cd server && pip install -r requirements.txt && python app.py
    Open http://127.0.0.1:5000. Upload any .ktr, .kjb, and .pdf. Hit Start translation. Verify progress steps advance, result table appears, download triggers.
  2. Run gateway unit tests
    pip install pytest responses schemathesis && pytest tests/gateway/ -v
  3. Run contract tests
    Start the server in one terminal, then: pytest tests/contract/ -v
    Schemathesis generates ~200 cases covering all endpoints and status codes defined in openapi.yaml.
  4. Run E2E tests
    npx playwright install --with-deps chromium && npx playwright test
    The Playwright config starts Flask automatically via a globalSetup fixture.
  5. Connect to a real upstream
    Open Gateway Settings (gear icon), disable Mock mode, enter your base URL and auth. Hit Save and test connection. If the health check returns HTTP 2xx, the gateway is wired. Run the full upload → translate → download flow.
  6. Lint
    flake8 server/ --max-line-length=120 (Python)
    For the JS, since there's no build, npx eslint migration-app/ --ext .js with a minimal flat config catches typos without requiring a bundler.

11. GitHub-driven feature evolution

Issue templates

TemplatePurposeRequired fields
bug.ymlGateway or UI defectSteps to reproduce, expected vs actual, mock vs real API
feature.ymlNew capabilityUser story, acceptance criteria, which layer(s) affected
adapter.ymlNew source/target platform (e.g. Informatica → DataStage)Source platform + version, target platform, sample file(s) to share

Branch and PR conventions

  • Branch names: feat/<issue-number>-short-slug, fix/<issue-number>-short-slug.
  • Every PR must reference an issue: Closes #42 or Relates to #42.
  • PR description template includes: What changed, How to test locally, Config changes (any new config.default.json keys), OpenAPI changes (yes/no — triggers backend team review).
  • Required reviewers: one for UI-only PRs, two for gateway/contract/OpenAPI PRs.

Labelling for triage

layer:ui layer:gateway layer:contract layer:backend breaking-change adapter-request good-first-issue

The breaking-change label auto-requests a review from a maintainer and blocks merge until the docs/api-contract.md update is included in the same PR.

Adding a new source/target adapter (the main extension path)

  1. Open an adapter.yml issue. Attach sample input files.
  2. Add the new file extensions to the KINDS map in app.js (or introduce a new kind key).
  3. Add the new gateway route(s) to app.py if the upstream API shape differs.
  4. Add the new endpoint and response-map fields to config.default.json and the Settings dialog.
  5. Extend openapi.yaml with the new schema types and paths. Label the PR breaking-change if existing fields change.
  6. Add a mock branch in mock_api() (gateway) and a new case in mock-api.js (browser).
  7. Add E2E spec covering the new upload → translate → download path.

12. Security baseline (non-negotiable)

  • Gateway binds to 127.0.0.1 by default. Set HOST env var only when behind an authenticating proxy.
  • Secrets (token, password) are masked before sending to the browser. server/config.json is in .gitignore.
  • Set ADMIN_TOKEN before sharing beyond localhost. The /admin/* routes can reconfigure which server the gateway calls.
  • Production: run behind gunicorn + TLS terminator (nginx or a cloud load-balancer). Never use the Flask dev server in production.
  • Container base image: registry.redhat.io/ubi9/python-311-minimal, non-root user, read-only filesystem.
  • Dependency scanning: Mend or pip-audit added to ci.yml as a separate job on every PR.
  • No credentials in logs. The upstream() function never logs request objects. Keep it that way.

The architecture's central invariant is the configuration firewall: the browser only sees stable /api/* routes; the gateway translates them to whatever the upstream requires, with no code changes. Every future adapter, auth scheme, and API evolution should be expressible entirely through config.json edits and the Settings dialog. When a change genuinely requires code, it belongs in exactly one of the two seam files — api.js or app.py — and must be accompanied by a test.
